# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A **curated awesome list** — *Awesome Agentic Engineering* — about building reliable, observable, production-grade agentic AI systems. It is a maintained public resource, **not an application codebase**. Most work here is README/Markdown curation, PR review, issue triage, and link/format hygiene.

Editorial stance (from `CONTRIBUTING.md`): **Reliability over novelty · Evaluation over intuition · Architecture over tooling ·** Apply this lens to every inclusion decision and maintainer comment.

## Layout

- `README.md` — the canonical list; the primary content file **when the task explicitly asks for list curation, entry updates, PR resolution, or issue-to-entry work**. Otherwise, don't modify it (or any content file) without a clear instruction.
- `appendix/` — overflow/fast-moving sections (browser agents, voice, creative, CRM, models, learning, newsletters, product lists).
- `CONTRIBUTING.md`, `RUBRIC.md`, `ANTI-PATTERNS.md`, `appendix/benchmark-and-evidence-policy.md` — the curation contract. Read these before judging any entry.
- `CHANGELOG.md` — every content change adds a bullet under `## [Unreleased]`.
- `.github/` — issue/PR templates, workflows, `scripts/find-stale-entries.mjs`.
- `docs/` and `assets/github/` — **generated** site output. Don't hand-edit; it's regenerated by the phase-7 publish workflow.

## Curation bar (the gate for every entry)

Score against the seven dimensions in `RUBRIC.md` (each 0–3): Reliability ×3, Evidence ×3, Agentic relevance ×3, Uniqueness ×2, Maturity ×2, Licensing ×1, Community signal ×1.

- **Merge requires weighted total ≥ 27 / 45.**
- **Hard gates — any `0` blocks merge:** Reliability, Evidence, Agentic relevance.
- Community signal (stars/adoption) is **tiebreaker only** — never sufficient, never offsets a hard-gate failure.

## What belongs / what does not

**Belongs:** agent architectures, orchestration, memory, evaluation, protocols and standards, tool use, multi-agent systems, and agent authority/identity/permissions/auditability/production operations — with engineering substance and real-world signal.

**Does not belong** (see `ANTI-PATTERNS.md`): generic LLM wrappers with no agentic primitives; vendor marketing/launch posts; unverified or launch-day benchmarks; duplicates that add no new structure or judgement; archived/abandoned/single-author prototypes framed as production; stars-as-evidence; out-of-scope tooling (chat UIs, prompt-only utils); rubric-restatement without applied judgement.

## Evidence rules

- Every substantive claim carries a tag: `[official]`, `[benchmark]`, `[field report]`, or `[author assessment]`.
- Prefer **official sources, papers, canonical repos, datasets, durable docs/project pages** over thin wrapper pages or marketing landing pages.
- Separate **benchmark performance** from **production maturity** — a benchmark proves workload fit, not reliability.
- No GitHub-stars-as-evidence.
- **Neutralise or remove** promotional language, time-sensitive "new/now" framing, rankings, pricing, and unsupported superlatives ("best", "state-of-the-art", "production-ready") unless backed by cited evidence.

## Description style

Neutral, engineering-focused, concise. Describe *what it is* and *what it demonstrates* — architectural strengths, operational constraints, governance fit, workload suitability. No adjective-heavy copy. Match the exact template/table layout of the surrounding section (see `CONTRIBUTING.md` → Formatting).

## README / formatting rules

- Match surrounding formatting **exactly** — column order, bullet template, emoji, casing.
- Section placement: put each entry in its single best-fit section; don't mirror the same item across sections without a justified distinction. Use the `appendix/` files for fast-moving or domain-specific lists.
- Refresh the `Last reviewed: Month YYYY` marker in any rapidly changing section you touch (e.g. Memory Systems, Spec-Driven Development, appendix product lists).
- Add a one-line entry under `## [Unreleased]` in `CHANGELOG.md` for content changes.

## Link quality

- Every link must resolve and point to the **canonical** destination (repo/docs/paper), not a redirect or aggregator.
- Check for duplicates across **both** `README.md` and `appendix/` before adding.
- Run the link checker locally (below) when you add or change links.

## Local checks (Node 20; advisory in CI, never block merge)

Run these for link changes, content additions, structural edits, and larger Markdown changes. They're optional for tiny typo-only edits, unless the surrounding file was already being checked.

```sh
# Markdown style
npx -y markdownlint-cli2 "**/*.md" "#node_modules"

# Broken-link check (single file)
npx -y markdown-link-check -c .markdown-link-check.json README.md

# All tracked markdown
git ls-files "*.md" | xargs -I {} npx -y markdown-link-check -c .markdown-link-check.json {}

# Stale-entry / freshness audit (default threshold 9 months)
node .github/scripts/find-stale-entries.mjs
FRESHNESS_MONTHS=12 node .github/scripts/find-stale-entries.mjs
```

> On Windows use the Bash tool for the `git ls-files | xargs` pipeline (POSIX syntax).

## PR triage workflow

1. Identify type: new entry · refresh · structural change · fix.
2. Read the cited evidence **first**. Missing evidence → request sources before scoring.
3. Score the seven dimensions; check the three hard gates.
4. Check section placement and duplicates (README + appendix).
5. Verify links resolve and formatting matches the surrounding block.
6. Confirm `Last reviewed:` and `CHANGELOG.md [Unreleased]` are updated where applicable.
7. Decide (below) and leave a terse, cited maintainer note.

## Issue-to-entry workflow

- New-entry issues use the structured template (name, URL, category, rubric fields). Convert to an entry only once evidence clears the hard gates.
- For underspecified suggestions, ask for the canonical source and the uniqueness angle rather than drafting from a marketing page.
- Place per the issue's category, but override placement if a better-fit section exists.

## Decision: accept / edit / request / close / park

- **Accept as-is** — clears hard gates, total ≥ 27, formatting clean, links resolve.
- **Edit as maintainer** — make the change yourself when the fix is **small and safe**: typos, formatting/column alignment, link normalisation, neutralising promo wording, adding a missing evidence tag you can verify, refreshing a `Last reviewed:` date. Don't bounce these back to the contributor for friction's sake.
- **Request changes** — substantive evidence/uniqueness/scope gaps the contributor must resolve. Name the specific dimension(s) and what would clear them.
- **Close** — clear anti-pattern, out of scope, or duplicate with no added judgement. Be kind and point to `CONTRIBUTING.md` / the relevant `ANTI-PATTERNS.md` item.
- **Park** — promising but blocked on a hard gate (e.g. too new to have reliability signal). Note what evidence would unblock it and revisit.

## Maintainer communication style

Warm, concise, respectful, low-friction. Thank the contributor, give a clear reason tied to a specific rubric dimension or policy line, and link the canonical doc. Prefer fixing small things yourself over a round-trip. Never gatekeep on tone; gate on the rubric. Preserve the maintainer's concise, engineering-led voice; do not over-explain, over-apologise, or dilute firm curation decisions.

## Scope guardrails

- Do not modify `README.md`, `appendix/`, or other content files unless the task explicitly asks — this file's creation does not authorise content edits.
- Don't hand-edit generated `docs/` site output.
- Keep this file lean; it loads into every session's context.
